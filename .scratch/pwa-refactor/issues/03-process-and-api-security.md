# 03 进程模型与 API 安全模型

Type: grilling
Status: resolved

## Question

Web 形态下「本地服务」的进程与安全决策（HITL，需用户确认）：

1. **启动方式**：开始菜单快捷方式 → exe 启动服务并自动打开浏览器？还是用户手动开浏览器访问？
2. **服务生命周期**：关掉浏览器标签后服务退出，还是常驻（托盘）？扫描进行中关浏览器怎么办？
3. **单实例与端口**：二次启动的行为（唤起已有实例并开新标签？）；固定端口被占用时的策略。
4. **API 防护（关键）**：这是能删文件的 localhost API，必须防两类威胁——
   - 其他本机进程/网页通过 CSRF、DNS rebinding 调用删除 API；
   - 用户误触。
   候选：随机 token 注入启动 URL、`Origin`/`Host` 校验、删除类操作要求带一次性确认令牌、敏感操作二次确认沿用 GUI 语义。如何组合？
5. **提权流程**：`RestartElevated` 后新进程是独立服务实例，浏览器会话如何接续（轮询原端口？提权实例用新端口并跳转？）。

约束：四道保险语义不变；强制预览在 Web UI 仍成立。

## Answer

**结论：空闲自动退出、状态文件单实例、五层 API 防护、同端口自动重连。（2026-08-31 与用户 grilling 确认，四问全按推荐采纳）**

启动方式不在此重复决策——工单 02 已定（快捷方式 → exe 起服务 + 自动开浏览器）。

1. **服务生命周期 = 空闲自动退出**：无进行中的扫描/清理任务且所有浏览器连接断开超过宽限期（30 秒，实现期可调）→ 进程自行退出。不引入托盘图标与 `H.NotifyIcon` 依赖。扫描/清理进行中关浏览器 → 任务照跑，完成后才进入空闲倒计时；重开浏览器即重连取回结果。

2. **单实例与端口 = 具名互斥体 + 状态文件**：
   - 首个实例起服务后把「实际端口 + 本次随机 token」写入 `%APPDATA%\Kleaner\service.json`；
   - 二次启动发现互斥体已存在 → 读状态文件 → `Process.Start` 打开浏览器指向已有实例 → 自身退出；
   - 端口策略：默认固定端口（如 45172），被外部进程占用则回退随机高端口并更新状态文件；
   - 互斥体允许提权后的新实例短暂重试获取（衔接第 4 条）。

3. **API 防护 = 五层，全部服务端强制**（前端只是配合，两层互不替代）：
   1. 只绑 `127.0.0.1` 回环（工单 01 已定，防局域网暴露）；
   2. Host 校验：`Host` 头必须恰为 `127.0.0.1:<port>`（防 DNS rebinding）；
   3. Origin 校验：非 GET/HEAD 请求 `Origin` 必须存在且等于 `http://127.0.0.1:<port>`（防跨站 CSRF）；
   4. 启动 token：每次进程启动生成随机 token，注入启动 URL，前端存 `sessionStorage`，所有 API 请求带 `X-Kleaner-Token` 头（中间件统一校验；防本机任意进程探测直连）；
   5. 删除类端点确认闸：`clean --apply` 类操作必须携带**此前预览返回的 `planId` + 一次性 `confirmToken`**——没有先调 dry-run 就拿不到 apply 凭据。UI 二次确认对话框是产品语义，服务端凭据是安全语义。

4. **提权后会话接续 = 同端口同 token + 前端自动重连**：提权实例沿用同一端口与 `service.json` 里的 token；前端发起提权重启前进入「重启中…」状态，对 SSE/API 指数退避重试，重连成功后整页刷新状态（会话从服务端恢复）。对浏览器而言只是「服务重启了一次」，同一套重连逻辑覆盖 Velopack 更新重启（工单 02）。窗口期端口被抢属极低概率且可检测（token 校验失败即报错重开）。
