# 关闭隔离区移动路径的检查-移动间隙：句柄锚定祖先 + 基于句柄复验

工单 10 的 C 项指出：`EnsureNoReparsePoints` 对路径的 reparse point 检查与实际 `File.Move` / `Directory.CreateDirectory` 是分离的调用（如 `QuarantineManager.Execute` 的逐项移动段），存在 TOCTOU 窗口——检查之后、移动之前，同权限进程可以把源路径的某个祖先目录替换为 junction，使 `File.Move` 实际移动一个**未经复验的对象**，或把落点引出隔离区。隔离区移动是全仓唯一的删除出口，这一窗口直接威胁 Phase 0 宪法的两条不变量：「移动的对象 = 执行时复验过的对象」与「落点 = 当前隔离区批次内」。本 ADR 决定用**句柄锚定**关闭该窗口。

## 决定

移动的整个检查-移动区间内，对**源文件全部祖先目录与目标祖先目录**以不共享写/重命名/删除的方式持有打开句柄（目录句柄，`FILE_SHARE_READ` only），并在**打开的同一个对象上**按句柄复验 reparse point 属性，然后才执行 `File.Move`：

1. 先以 `FILE_FLAG_OPEN_REPARSE_POINT` 逐级打开源与目标的每个现有祖先并持有到移动结束；被锚定的目录在该区间内无法被重命名、替换或挂链接（无 `FILE_SHARE_DELETE` 的打开句柄会令 Windows 拒绝对目录的改名与删除），间隙因此从「毫秒级无保护」变为「被句柄物理关闭」。
2. reparse point 复验改为读句柄上的文件属性（`GetFileInformationByHandle`），与被锚定的对象一一对应，替代按路径名的重复 `File.GetAttributes` 扫描。
3. 叶子文件仍走 `File.Move`，但源与目标两端的关键祖先此时已被钉住；若任一祖先无法以要求的方式打开（含被替换为 reparse point 后属性复验失败），整项跳过并计入 `Skipped`，绝不移动。
4. **残余边界如实声明**：不承诺对抗管理员权限攻击者（可强行关闭句柄）、内核级竞争或本地物理访问；目标盘符根目录（如 `D:\`）在进程外被整盘改写同样超出范围。这些边界写入 `docs/deletion-path.md`，不夸大。

**验收是收口条件的一部分**：自动化回归（junction 在检查后、移动前被替换的受控竞争，可用故障注入点复现）之外，必须按 goals.md「证据优先」在真机完成并行进程 + junction 的对抗验收，验收记录进入工单 10。

## Considered Options

- **事后校验（移动后确认落点仍在批次内、源文件已消失）**：拒绝。边界已被穿越之后才报警，违反「失败时保留数据」的精神；补救（把误移文件搬回）本身又要经过同样不可信的路径。
- **纯路径检查的重试循环**：拒绝。检查与使用仍是两个操作，窗口只是被缩小和随机化，无法证伪；重试还与「占用文件跳过」语义冲突。
- **open-by-handle 整体改名（`SetFileInformationByHandle(FileRenameInfo)`，句柄级重命名）**：技术上更彻底（连叶子移动都不再经过路径），但需要为叶子与目标父目录各开句柄并处理跨目录改名、长路径与共享冲突，改动面与失败模式显著更大。**列为升级路径**：若句柄锚定方案的真机对抗验收仍能复现竞争，再升级到句柄级改名，作为独立修订重开本 ADR。
- **接受残余风险只加文档**：拒绝。这是唯一删除出口，窗口对「清理范围越界」与「落点逃逸」两类不变量都是直接威胁，且有明确可行的关闭手段。

## Consequences

- `QuarantineManager` 将引入少量 P/Invoke（目录句柄打开与句柄属性读取），集中在 Executor 层；`Kleaner.Core` 不受影响，不改依赖方向。
- 每项移动新增数次目录句柄打开/关闭；祖先层级通常只有 3–5 级，预计不构成性能问题，但仍以基准为准，不宣称满足 SLO。
- CLI 与 GUI 共用 `QuarantineManager.Execute` / `RestoreBatch`，两个入口自动同时收口，无需分别修改；还原方向（从隔离区移回用户目录）同一套锚定策略，落点逃逸窗口一并关闭。
- 锚定失败（祖先被占用、权限异常）会表现为新增的跳过项，报告与 UI 文案需同步；测试夹具继续只用临时目录。
- 若 Windows 未来提供无 P/Invoke 的原子「检查并移动」，可重开本决策简化实现。
