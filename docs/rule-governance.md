# 规则治理指标（Phase 2 / 工单 rule-governance 01）

goals.md Phase 2 要求「目标从规则数量改为目标软件覆盖率、证据覆盖率、验证覆盖率、推荐准确率和误伤事件数」。本文件给出**可测量口径**与首份基线。测量工具：`Kleaner.ScanCli governance-report`（纯规则库只读测量，不扫描文件系统、不写状态）。

## 可测量口径

| 指标 | 口径 | 数据源 | 状态 |
|---|---|---|---|
| 软件覆盖率（分类） | 6 个 `RuleCategory` 分类中已有规则的数量 / 6 | rules.v1.json | ✅ 已实现 |
| 软件覆盖率（目标根） | 规则 `paths` 开头的唯一目标根数（`%环境变量%` 或盘符，大小写不敏感去重；**不展开实际路径**——保证指标跨机器确定性） | rules.v1.json | ✅ 已实现 |
| 证据覆盖率 | `safetyNotes` ≥ 20 字 **且** `safetyDoc` 锚点非空的规则占比 | rules.v1.json + RuleSetLoader 语义 | ✅ 已实现 |
| 验证覆盖率 | `verified` 以「本机实测」开头的规则占比（与 `RuleSelectionPolicy.IsDefaultSelectable` 默认勾选同源） | rules.v1.json | ✅ 已实现 |
| 推荐准确率 | **精确定义待定**（候选口径：默认勾选规则的用户扫描命中分布、勾选后跳过率）。当前无用户行为遥测（goals.md 隐私边界：默认完全离线），无法离线计算——**如实标注为待定义** | 需用户侧数据模型 | ⏳ 待定义（工单 02/03） |
| 误伤事件数 | **口径待用户确认**（还原=误伤的代理信号？） | 隔离区还原历史 | ⏳ 待定义（工单 02） |

实现：`Kleaner.Core/RuleGovernance.cs`（纯函数 `RuleGovernance.Report(RuleSet)`，xunit 6 项覆盖全达标/部分/空库/去重/短说明）。

## 首份基线（2026-09-10，rules.v1.json @ main）

```
规则总数               101
证据覆盖率            100.0%  （101/101）
验证覆盖率             23.8%  （24/101）
默认勾选规则数          24
分类覆盖              6 / 6
唯一目标根               5   （%TEMP% %LOCALAPPDATA% %WINDIR% 等环境变量根）
```

解读：证据覆盖率满分（Phase 0 工单 11 的成果：所有规则都有安全性说明与文档锚点）；验证覆盖率 23.8% 与「只有本机实测的 24 条默认勾选」的产品语义一致——**验证覆盖率低不是缺陷而是保守策略的体现**，提升它的途径是真机实测更多规则而非放松口径。

## 目标值与阈值

**未设定**——属产品决策，需以本基线为锚点确认（工单 rule-governance 03，blocked 等用户输入）。冻结 SLO 的经验（先基线后冻结、范围限定显式声明）同样适用于治理指标。

## 已知局限

- 「推荐准确率」无法离线计算：需要用户侧勾选/跳过行为的遥测数据，而 goals.md 隐私边界禁止默认遥测。任何准确率数字必须来自显式 opted-in 的数据源。
- 「误伤事件数」口径待确认（还原=误伤的代理有噪声：还原也可能是「改主意」）。
- 目标根计数不含真实路径展开——同一环境变量在不同机器指向不同目录，指标因此跨机器稳定但精度有限。
